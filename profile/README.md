<p>聊到 API 用的住宅 IP，报价单上通常同时躺着四种计价单位：按流量、按条月租、按并发端口、按小时。拿同一份需求去问三家，报出来的数字能差三倍，原因不是谁在坑人，而是各自默认的口径不同。这篇不比较谁便宜，而是把一笔月度支出拆成调用量、并发、出口形态、运维替换四个可计算的部分，让你自己把预算算出来，再拿去和供应商对齐口径。</p>

<h2>一、先把一笔账单拆成四个可计算的部分</h2>
<p>API 场景和网页登录场景的成本结构差别很大。网页登录的瓶颈是账号数，接口调用的瓶颈是请求量和并发。先把用量写成数字，再谈单价，能避免"先买十台服务器再发现用不上"。</p>
<h3>调用量：换算成每月的请求数与字节数</h3>
<p>取最近一周的日志，统计日均请求数、平均输入与输出 token 数。按一个中文字约 1.5 至 2 个 token 粗算，再把 token 换成字节量级：一次短请求上下行通常几 KB 到几十 KB。这个数字决定了按流量计费时的底价。</p>
<h3>并发：决定端口数与出口条数</h3>
<p>并发不是日均请求数除以秒数，而是"同一瞬间在飞的请求数"。用压测或日志里的最大重叠数去估，通常比平均值高 3 到 5 倍。并发定错，要么端口不够排队，要么买多了闲置。</p>

<h2>二、第一笔账：调用量小的时候，流量费根本不是主要支出</h2>
<p>很多人一听"住宅代理按 GB 收费"就把预算做得很高，实际算下来往往相反。纯接口调用的流量非常轻，真正占大头的通常是地址月租和值守人力。</p>
<h3>把 token 换算成 MB 再乘以单价</h3>
<p>举个可复算的例子：每天 3000 次调用，平均上下行合计 15KB，一天约 45MB，一个月约 1.35GB。动态住宅代理的流量单价常见在每 GB 几美元到十几美元区间，仅供参考，按此折算的月成本通常只有几十元级别。相比之下，一条静态独享住宅地址的月租常见在每条几十元到两三百元区间，也是仅供参考，往往会先撞到这个数字。</p>
<h3>什么时候流量会突然变成大头</h3>
<p>三类情况要小心：一是把整篇文档塞进 prompt 做批量处理，输入 token 暴涨；二是流式输出长文本，响应体随之变大；三是把图片、日志、中间结果也走代理通道。这三种情况下，压缩请求体、把非必要流量移出代理，比换供应商省得更多。</p>

<h2>三、第二笔账：并发口径问不清，预算一定做不准</h2>
<p>"支持 100 并发"这句话至少有三层含义：同时建立的 TCP 连接数、同时处理的请求数、允许绑定的账号数。三者数量级不同，报价也完全不同，签约前必须让对方写清是哪一种。</p>
<h3>用峰值而不是均值定端口</h3>
<p>取两周日志里的每分钟请求数，找出最大的三个时间点，按单请求平均耗时换算成并发：并发约等于每分钟请求数乘以平均耗时秒数再除以 60。给这个结果留 30% 余量，就是你需要买的端口规模。</p>
<h3>排队和超时比买贵更伤</h3>
<p>端口不足时请求会在本地排队，表现为首字节时间忽高忽低，重试率上升，账单反而更高。先把客户端连接池上限、读取超时、重试次数三件事配好，再判断是不是真的需要加端口。</p>

<h2>四、第三笔账：预算弹性藏在出口形态的搭配里</h2>
<p>没有一个方案能同时便宜又稳定，但可以做组合：把稳定要求最高的那部分流量放在固定出口，把探索性、批量的流量放在按流量计费的池子里。这样既能保住核心业务的成功率，又不会为边缘需求付独享的钱。</p>
<h3>核心链路用固定出口</h3>
<p>面向正式业务的调用、需要和账号资料对齐的部分，放在一到两条静态独享地址上，长期不变。单价高，但数量少，总价可控，排障也简单——出问题只需要看一条线的曲线。</p>
<h3>边缘任务用池化流量</h3>
<p>数据清洗、离线评测、多地区抽样，这类任务对出口是否固定不敏感，用按流量计费的池子更划算。注意给这类任务单独设密钥和配额上限，避免失控的脚本把预算烧穿。</p>

<h2>五、第四笔账：替换、停机与人力，最容易漏算</h2>
<p>前三笔是明账，第四笔是暗账。地址被投诉、线路抖动、供应商调整机房，任何一次都意味着停机、重新验证、重新观察。把这三类事件按年发生次数折进去，很多"每月省 50 元"的选择会立刻反转。</p>
<h3>给每次替换标一个工时价</h3>
<p>替换一条地址的实际动作包括：提交工单、等待生效、改配置、跑验证脚本、观察 24 小时。按两小时人力计，若一年换六次，就是十二小时。这笔钱通常远大于月租差价，谈判时可以直接拿来要求更长的稳定期承诺。</p>
<h3>把可用率写进验收标准</h3>
<p>不要接受"很稳定"这种描述，要求给出可核对的指标：月度可用率、平均故障恢复时长、替换工单的响应时限。三项都能量化的供应商，后续扯皮会少很多。</p>
<h3>预留一条备用出口</h3>
<p>哪怕只多花一条地址的钱，也建议保留一条不同上游的备用线路。切换脚本提前写好，故障时改一个环境变量就能切过去，比临时找供应商要地址快得多。</p>

<h2>常见问答</h2>
<h3>调用量很小，还有必要用住宅 IP 吗？</h3>
<p>答：看用途。内部测试、离线评测对出口类型不敏感，机房出口通常够用；如果调用需要和正式账号、账单资料保持同一环境，出口类型就要跟着账号走，这时候用量小也得配，只是可以选最小的规格。</p>
<h3>按流量计费会不会突然超支？</h3>
<p>答：会，而且多数超支来自脚本而非业务。给每个密钥设日配额和告警阈值，把重试次数限制在 2 次以内，避免失败请求反复重发；再定期看流量曲线，异常尖峰通常一眼能看出来。</p>
<h3>并发端口买多了能退吗？</h3>
<p>答：多数按月计费的方案不支持中途降配，所以宁可从小的起步，观察一周再扩。真要弹性，选按小时或按天计费的形态做峰值补充，长期底座仍然用月付。</p>
<h3>静态独享和动态池，哪个总成本更低？</h3>
<p>答：取决于出口是否需要固定。需要长期同一出口的场景，动态池看似便宜，但每次地址变化都要重新适应，隐性成本高；反之，一次性批量任务用静态地址就是浪费。按任务性质分开算，比整体比价准确。</p>
